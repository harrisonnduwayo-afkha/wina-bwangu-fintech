# Wina Bwangu

Mobile money management web app for a six-booth Lusaka network (Airtel Money, MTN Money, Zamtel Money, Zanaco, FNB). University project: client-side prototype (Logbook 2) and server-side prototype with tests (Logbook 3).

**Live demo:** [https://harrisonnduwayo-afkha.github.io/wina-bwangu-fintech/](https://harrisonnduwayo-afkha.github.io/wina-bwangu-fintech/)
Demo login (demo account only, not a real credential): `admin` / `wina123`

The live demo runs in browser-only mode (data kept in your browser). Run the Node server below to use the SQLite database.

Node.js server (REST API) + SQLite database + the responsive Wina Bwangu web app. **No npm packages to install.** Needs Node.js 22.5 or newer.

## Run it

```
npm start
```

Open [http://localhost:3000](http://localhost:3000) and sign in with **admin / wina123** (demo account; set `WINA_ADMIN_PASSWORD` before the first start to change it). The database file is created at `data/wina.db` on first start and loaded with the 308 transactions of Appendix 1.

Optional settings: `PORT`, `WINA_DB` (database path), `WINA_SECRET` (token signing key; random per start if not set).

## Tests

```
npm test            # 41 unit tests + 44 regression/API tests (about 1 second)
npm run test:ui     # 30 browser tests incl. responsive sweep (needs: npm i -D playwright && npx playwright install chromium)
```

The full test plan and recorded results are in `docs/Test_Plan_and_Results.docx`.

## Structure

```
server/logic.js      pure business rules (IDs, tax, credit, validation, summaries)  <- unit tested
server/db.js         SQLite schema, seeding from Appendix 1, queries, atomic insert
server/server.js     HTTP server: REST API, token auth, rate limiting, static files
public/index.html    responsive web client (uses the API when served by the server)
tests/unit           unit tests
tests/regression     API + golden-value regression tests
tests/ui             browser and responsive tests
docs/                test plan generator and document
```

## API (all JSON; everything except login and health needs `Authorization: Bearer <token>`)

| Method and path                                                 | Purpose                                                                                                    |
|-----------------------------------------------------------------|------------------------------------------------------------------------------------------------------------|
| POST /api/login                                                 | `{username,password}` returns `{token,user}`                                                               |
| GET /api/config                                                 | booths, locations, services offered, rates, limits, tax rate, capital                                      |
| GET /api/transactions?booth=&service=&status=&q=&limit=&offset= | list and search                                                                                            |
| POST /api/transactions                                          | `{booth,service,amount,date?}`: validates, checks credit, generates the next ID, saves, returns the record |
| GET /api/credit?service=                                        | used, remaining and status for a service                                                                   |
| GET /api/summary                                                | totals, per-service credit, revenue per booth, frequency matrix                                            |
| POST /api/admin/reset                                           | admin only: restore the original 308 transactions                                                          |
| GET /api/health                                                 | liveness check                                                                                             |

## Case study rules implemented

- TransactionID = `WB` + 7 digits, generated by the server inside the same database transaction that saves the record (no duplicates, even with simultaneous requests).
- Revenue = amount x revenue per kwacha. **Tax = 16% of revenue** (assumption: the case study gives no rate; change `TAX_RATE` in `server/db.js`). Revenue after tax = revenue - tax. Transaction amount after tax = amount - tax.
- A request is refused if the booth does not offer the service or the amount is more than the service's remaining monthly credit.
- Total capital = sum of monthly limits = K740,000.
- Data note: Appendix 1 contains one transaction (WB0000017) for Zamtel Money at Wina5, which the case study does not list for that booth. It is kept as supplied.

## Security measures

Parameterised SQL only; input validation on the server; scrypt-hashed passwords; signed expiring tokens; login rate limiting (5 failures per 5 minutes); request size limit; path-traversal protection on static files; security headers; no secrets in the client.

## Responsive design

Fluid grid layout, breakpoints from 380 px to 1700 px, navigation that collapses to a menu button and slide-in drawer on phones, 44 px touch targets, scrolling tables, scaling images and charts, reduced-motion support. Verified at 320, 375, 768, 1024 and 1440 px.

The site detects whether the Node API is available. On GitHub Pages or when opened from disk (no API) it falls back to browser-only mode, so the same `index.html` works everywhere. Opening `index.html` straight from disk still works as a browser-only prototype (data kept in the browser) for Logbook Exercise 2.
